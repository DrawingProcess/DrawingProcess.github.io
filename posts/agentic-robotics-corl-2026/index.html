Agentic Robotics at CoRL 2026

Frontier models can write control code, inspect observations, and coordinate robot tools. The research question is how to turn that capability into timely, reliable physical work.

A community reconsidering its assumptions

The summary frames reactions to Astra's reported September 3 release through a humorous sequence of denial, anger, bargaining, depression, and acceptance. It describes skepticism about selected demonstrations, arguments about the continued need for motion planners, and concern that programming ability might absorb work previously treated as a research specialty.

This narrative describes reactions reported in the video. It does not establish a measured consensus among robotics researchers. The technical question behind it is which capabilities a stronger general model supplies and which still depend on robot-specific data, controllers, and testing. Community reactions, 0:26–1:09

Three places to put the agent

Generate the next action program

The described loop reads observations, writes commands, runs them, and inspects fresh images, including wrist views. Its program becomes a temporary controller. The API determines the difficulty: calling a validated move-to-pose primitive differs from issuing raw joint commands. Tool access, privileged state, and human assistance belong in the experimental description. Observation and code loop, 2:51

Coordinate specialized skills

An orchestrator can choose goals, invoke a planner or learned policy, check progress, and select a recovery. As an architectural inference, this allows slow reasoning above a faster local feedback loop. The interface needs explicit preconditions, valid actions, termination criteria, and failure reports. Mistaking partial progress for success sends subsequent steps toward the wrong state.

Help build and test the system

The summary describes agents constructing simulations and working with experts in real-to-sim-to-real iterations. Here, the model assists development before or between deployments. Generated scenes and tests need checks for geometry, contact behavior, and whether their success criteria reflect the intended work. Simulation and development, 3:25 · Human review, 4:09

The gap between solving a task and doing useful work

Latency changes the state being controlled

A scene may change while the model reasons. Long calls are particularly consequential for moving objects, maintained contact, and work near people. Measure sensing, reasoning, action execution, and retries together. Throughput—accepted completed jobs divided by elapsed operating time—captures waiting and recovery. Report it alongside success rates and latency distributions. Latency, 5:26 · Throughput, 9:36

Physical mistakes alter what happens next

A dropped or damaged part can change subsequent work. The summary contrasts this with code changes that can often be reverted. Define an action envelope, force and collision limits, intervention rules, and stop conditions. Completion judgments also need scrutiny: a visually plausible placement can leave a connector unseated. Physical consequences, 5:58 · Completion judgments, 6:16

Contact exposes missing information

The summary identifies contact-rich dynamics as a data gap. Language and visual knowledge may suggest a strategy, while execution depends on friction, compliance, forces, and occluded geometry. Experiments should isolate task reasoning, state estimation, contact control, and completion detection to identify where the failure originates. Contact-rich interactions, 9:41

Specialization is a system design choice

The summarized speakers argue for specialized models where latency, power, cost, and reliability constrain deployment. Compare a general orchestrator with a fixed planner using the same local skills, then separately test direct code generation. Holding execution constant helps identify what reasoning adds. System-level questions, 8:01 · Specialized models, 8:31–9:16

Research directions

The following proposals are analysis developed from the summary.

  • Reasoning under a deadline. Vary the allowed inference time and measure whether better decisions offset waiting. Include moving and disturbed scenes.
  • Verifiable skill interfaces. Expose preconditions, progress, failure codes, and recovery options. Measure false completion and repeated failure.
  • Learning from deployment. Preserve contact failures, retries, and operator corrections. Test whether training on these cases reduces recurrence on held-out runs.
  • Persistent evaluation. Carry state across jobs and compare throughput, quality, interventions, and safety stops against independently reset episodes.
  • Auditing generated environments. Compare generated scenes and evaluators with independent checks and hardware measurements. Track review effort alongside generation speed.

These questions connect to the earlier comparison: GR00T 2 concerns policy transfer, DexBench controlled task evaluation, HolidayFactory persistent simulated jobs, and Gemini Robotics 2.5 integrated deployment. Robot Learning, November 2026

The closing perspective in the summary is that frontier models lower barriers and expand what robotics teams can attempt. Useful deployment then depends on tools, physical execution, measurement, and feedback from hardware. Closing perspective, 11:10
